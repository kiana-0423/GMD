# 输出层设计与优化

状态：设计中。本文中的记录、计划、sink（输出消费者）和异步管线均未实现。
优先减少输出引入的数据移动与额外计算；保持现有文件协议和旧 API 的兼容入口。
本轮不修改旧引擎源码、默认构建或物理基线。

## 1. 已确认的成本来源

当前 [`System::resize`](../../include/gmd/system/system.hpp) 会分配位置、速度、
力、质量、电荷和多种身份数组，即使消费者仅需轨迹坐标。复用一个输出专用
`System` 可以避免每帧重新分配，但仍占用多余存储，并可能增加主机数据复制。
[`TrajectoryWriter::write_frame`](../../src/io/trajectory_writer.cpp) 同时写 XYZ
和日志；当前接口无法仅写标量日志。其显式传入 2K 的重载已能避免扫描速度。

前版设计中的旧 `System` 桥接保留为过渡工具。长期路径提取独立的序列化核心，
直接读取轻量记录；旧 API 调用这个核心，以复用格式代码并保留已有入口。
是否缩短总运行时间仍需实测，不能把接口变化本身当作性能结果。

## 2. 输出请求提前进入执行计划

订阅声明记录类型、字段、频率、采样阶段和目标格式。初始化时校验能力与单位，
每步只更新哪些订阅到期，不引入按原子或边进行的动态分派。

```text
动力学需求 + 本步到期订阅 + 文件格式必需字段
    → 计算需求并集 → 有效时间层的捕获点
    → 同状态的字段去重 → 传输/输出记录 → 各 sink
```

- 热浴/压浴、接受率判定或其他动力学所需的能量、动能和维里必须照常计算。
  仅用于观测的量可以按订阅频率计算。关闭输出不能删除物理推进需要的工作。
- 日志、轨迹和 checkpoint 分开采样。同一步、同版本、同时间层的标量与坐标
  可共享一次捕获；时间层不同时不得因 step 相同而合并。
- 保留旧 XYZ 帧头时，轨迹订阅也需要 PE、KE、T、P 等对应字段，即使日志该步
  不到期。依赖由格式声明，不能只按记录名称推断所需计算。
- 只有标量日志时，传回固定大小记录，不下载每原子的坐标、速度、力；GPU
  归约本身仍可能随系统规模增长。仅需标量压力时不必传回完整九分量维里，
  但不能由此省略动力学或 checkpoint 所需的张量计算。
- 异步完成后的 writer 只序列化，不重新求力、不扫描速度求动能、不再次
  全局归约。标量从设备/通信阶段得到后复用。

## 3. 轻量记录与共享格式实现

| 设计记录 | 内容与存储 | 默认不携带 |
|---|---|---|
| `ThermoRecord` | step/time、采样阶段、状态版本、PE、2K、DOF、T、P、V、有效性与约束诊断；固定大小值 | 原子数组 |
| `TrajectoryFrameView` | 坐标只读视图、稳定 ID 顺序、类型元数据引用、盒、帧头的热力学记录与时间层 | 力、速度、邻居表、中间边张量 |
| `RestartRecord` | 一致时间点的动态状态、原子属性、拓扑/模型描述、积分与随机过程状态、所需维里及完成步记录 | 可由状态安全重建的工作缓冲区 |

上表是数据契约，不是已发布 ABI。捕获层拥有缓冲区；视图按明确布局/步长读取，
可以直接引用 SoA 主机数组，避免为 writer 强制构造逐原子对象。序列化核心
接受已就绪的主机视图，不识别 CUDA 指针。异步消费者须持有缓冲区租约，直到
读取结束；只复制一个 `span` 并不能延长底层存储寿命。

实现时将格式代码和只读记录契约组织为不依赖任一模拟引擎的库，可由 `next/`
独立构建。旧 `gmd` 入口通过外围依赖使用该库，新核心不依赖旧引擎；新 API
与旧 API 必须共享同一格式实现，避免长期维护两份 XYZ/日志序列化代码。
旧 `write_frame(System, ...)` 保留联合写两种文件的行为；新记录入口允许各自
写入。独立频率模式按 step/time 对齐数据，不承诺两个文件具有相同记录数。
需要逐帧对齐的旧消费者使用兼容的联合频率配置。

可选过渡桥接放在仓库外围集成目标，如 `integration/legacy_output/`：复用输出
专用 `System`，调用旧 writer 的显式 2K 重载。它不承担生产优化目标，仍受旧
联合频率和 `int` tag 限制；序列化提取完成后仅作为兼容对照，不进入新主路径。

## 4. 身份、静态元数据与物理语义

- 类型、质量、稳定 ID 和拓扑按相应版本缓存。GPU 重排后更新本地槽位到输出
  顺序的映射，身份/属性不变时不重复下载静态数据。类型或拓扑可变的模型必须
  更新版本。排队的帧保留其元数据版本，不能在写入前被新元数据覆盖。
- XYZ 没有 ID 列，行顺序必须由稳定全局 ID 确定，禁止直接使用当前 GPU 槽位。
  多设备仅汇集 owned 原子；检查缺失/重复，并明确标量的 local/global 状态，
  已全局归约的数据不能再次求和。普通日志不需要汇集每原子数据。
- 核心身份为 64 位。旧桥接和旧 checkpoint 读取器有 `int` tag 范围限制，
  导出前检查规模及 ID；不静默截断或重新编号。大 ID 的新格式另行版本化，
  使用轻量记录本身不代表旧格式限制已消失。
- 快照声明单位，格式边界仅转换一次。旧日志为 fs、Å、eV、K、bar；旧状态与
  checkpoint 压力为 eV/Å³，checkpoint 速度对应旧内部时间单位。内部规范见
  [算子契约](operator_contracts.md#1-单位与方向)；约化单位缺少换算尺度时拒绝
  导出成这些物理单位。轻量 writer 不假定所有字段都已转换为日志单位。
- 同一热力学记录的 PE、2K、W、V、T、P 属于同一状态。兼容旧 NPT 行为时，
  保留压浴缩放前的完成步热力学量与缩放后坐标的不同时间层及文件说明。
  捕获发生在各自的有效阶段；不能等整个时间步结束后从已改变的状态重构。
  初始帧无完成步记录时使用当前几何。
- 压力缺失沿用 `P_valid=0` 和 `nan`；零是有效物理值。DOF、约束诊断与维里
  完整性必须明确；没有约束与缺少约束信息不等价，不支持的状态须报告。

## 5. 捕获、下载与写入的生命周期

首版同步路径只等待本次输出所需的完成事件，然后直接下载已请求字段并写入。
事件等待不替代设备错误检查；不为输出引入每步全设备同步。按字段下载、
缓冲区复用和独立日志频率无需等待异步管线即可实现。

异步路径在已有正确基线和性能数据后引入：

```text
compute stream: 产生目标状态 → 打包到独立设备输出槽 → recorded(captured)
                → 下一步可修改原始 DeviceState
copy stream:    wait(captured) → D2H 到池内 pinned 主机槽 → recorded(ready)
writer:         等待 ready 并检查状态 → 读取/写入 → 释放槽与元数据租约
```

打包期间原始状态仍受读写依赖保护；独立设备输出槽在下载结束前不可复用，
主机槽在所有消费者读取结束前不可复用。若直接从 `DeviceState` 异步下载，
必须禁止其被改写直到下载完成，不能用异步 API 名称代替数据生命周期约束。
记录中的 step/time、盒及完成步标量也必须在捕获时固定。

打包可合并所需字段提取、稳定顺序重排与布局转换，避免在主机上再复制完整帧。
但它增加一次设备读写；简单同步下载可能更快，需比较后选择。类型等已缓存
元数据只引用其版本，不强制每帧重新打包。

队列和设备/主机缓冲池有显式内存上限，按已完成消费的槽复用，不按帧反复
分配或无限积压。默认队列满时等待空槽，并记录等待时间；轨迹和 checkpoint
不静默丢弃。每个文件由单一消费者保持顺序；退出前排空队列并检查关闭错误，
写入失败传回运行控制层。只有用户明确选择的监控流才可另定义丢弃策略。

CUDA 异步主机传输采用有界 pinned 缓冲池和显式 stream/event。能否与计算
重叠取决于硬件能力和实际依赖；不承诺零拷贝或完全隐藏 I/O。API 依据：
[NVIDIA CUDA Best Practices：异步传输](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#asynchronous-and-overlapping-transfers)
与 [pinned memory](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#pinned-memory)。

## 6. checkpoint 的单独边界

checkpoint 订阅要求一次可恢复的状态捕获。坐标、速度、盒、step/time、
模型和拓扑版本，以及已有热浴/压浴/随机状态必须对应同一恢复点；完成步
热力学量按其另行标注的时间层保存，不能从不同帧随意拼接。

静态数据可以在内存中共享，但导出的旧格式仍写齐所需内容；缓存不等于
删除恢复依赖。首版只支持已验证的固定盒 NVE 共同模型范围，缺少必要状态
或旧格式无法表达时明确拒绝。力和邻居表仅在恢复流程能正确重建时省略。

捕获后可以异步写文件，但“已提交”与“已完成写入”分别报告。后续实现采用
临时文件写入、检查 flush/close、完成后替换目标的提交协议，失败时保留上一份
完整 checkpoint；若承诺断电持久性，须另实现并验证文件系统同步语义。
普通轨迹允许持续追加，不与 checkpoint 共用提交完成的含义。

## 7. 分阶段验收与性能证据

实现顺序见[路线图](roadmap.md#输出接入的阶段验收)。性能比较使用相同原子数、
格式、字段、采样频率和存储介质，异步运行计时包含最终排空，不用入队速度
冒充文件输出吞吐量。分开测量下列成本，不把并行重叠的阶段耗时直接相加：

- 关闭输出的步耗时；仅标量日志；仅轨迹；联合轨迹/日志；checkpoint。
- 按字段下载的字节数、主机复制字节数、打包/下载/格式化/写入时间。
- 队列等待、峰值设备 staging/普通主机/pinned 内存、缓冲区分配次数。
- 输出步与非输出步的延迟，以及包含最终排空的总吞吐量。

可直接验收的结构指标：只记标量日志时每次下载字节数不随 N 增长；新路径
不构造旧 `System`，轨迹不下载力与速度；容量稳定时不按帧重新分配缓冲区；
同状态被多个消费者请求时不重复捕获。实际时间与内存收益另行报告。

正确性至少覆盖：日志/轨迹不同频率且 XYZ 帧头齐全、GPU 重排后的稳定行序、
元数据更新但旧帧尚未写入、队列耗尽/慢消费者/写失败、异步期间源状态改写、
初始帧与 NPT 时间层、无效压力、ID 范围、checkpoint 读回与续跑。格式提取
使用同一主机状态比较旧/新序列化结果；GPU 结果按数值容差比较，不要求所有
平台逐位一致。当前尚未执行上述输出验收。
